* The queue is not free

A one-second task with its own =sbatch= still waits in the queue, still writes a job record, and still starts a shell. A few thousand of those tasks can spend more time starting than working. A job array, from the Slurm episode, is the first improvement: one submission, many tasks, and Slurm still tracks each task.

A pilot job goes further. You ask Slurm for a block of cores once. A small manager sits inside that allocation and starts the short tasks itself. The queue saw one job.

* QCG-PilotJob on the course cluster

QCG-PilotJob is the pilot manager this course installs. It is a site module. It is not in the EESSI stack. =module spider QCG-PilotJob= inside EESSI 2025.06 says it cannot be found, and that is expected.

On the course cluster:

#+begin_src bash
module purge
module load 2024
module load QCG-PilotJob
srun --partition=thin_course --ntasks=1 --cpus-per-task=2 --time=00:05:00 \
  python3 episodes/files/exercises/qcg-three.py
#+end_src

=module load 2024= is the course alias for EESSI 2025.06. Load it before =QCG-PilotJob=. The script submits three tasks that each run =printf=, waits until they finish, and prints:

#+begin_src text
qcg-finished
task-0
#+end_src

The Python is short. A =LocalManager= runs the tasks on the machine where you started it. =Jobs= collects the descriptions. Each task asks for exactly one core.

#+begin_src python
manager = LocalManager()
jobs = Jobs()
jobs.add(name="job_0", exec="/usr/bin/printf", args=["task-0\\n"],
         stdout="out_0.txt", numCores={"exact": 1})
manager.submit(jobs)
manager.wait4all()
manager.finish()
#+end_src

On a cluster you normally put that manager inside one =sbatch= script, so the cores come from the allocation instead of from the login node. For three =printf= tasks the login node is an acceptable place to see the tool work. A real parameter sweep belongs in the job.

=qcg-pilotjob --help-h= prints the command-line help if you want the non-Python entry point. The exercises use the Python API because that is what the course stack is there to support.

#+begin_callout
If =module load QCG-PilotJob= fails, you are probably on the EESSI container or on a machine without the site module. Skip the run. The HyperQueue and Snakemake sections are still readable, and the QCG script is still in the lesson files for later.
#+end_callout

* HyperQueue

HyperQueue is the tool to reach for when the pilot should be a small server plus workers, and the workers are Slurm jobs. You start =hq server start=, you submit tasks to that server, and =hq alloc add slurm= asks Slurm for workers. The server fills the workers. You do not write one batch script per task.

The idea you should keep: the Slurm job is the bucket of resources. HyperQueue is who pours tasks into the bucket. You do not need to memorise every flag today.

* Snakemake

Snakemake starts from files. A rule names an output, the inputs it needs, and the command that builds the output. Snakemake runs a rule when the output is missing or older than the input. Three rules that feed each other are a pipeline:

#+begin_src python
rule all:
    input: "summary.txt"

rule step_one:
    output: "part.txt"
    shell: "printf 'part\\n' > part.txt"

rule summary:
    input: "part.txt"
    output: "summary.txt"
    shell: "cp part.txt summary.txt"
#+end_src

That is a different question from QCG. QCG asks how to run many copies of a command. Snakemake asks which files are out of date. People combine them: Snakemake decides the graph, and a cluster profile or a pilot runs the commands.

* FireWorks

FireWorks stores tasks in a database, with dependencies, and workers pull the tasks. You use it when many people submit tasks, when a task must be retried, or when you need a record of what ran. It is more machinery than a three-task =LocalManager=. If your whole problem is "run this command on these fifty inputs today", stay with the array or with QCG.

* Which tool answers which question

| Tool | When you reach for it |
|--------------+--------------------------------------------------------------|
| QCG-PilotJob | a Python script should launch tasks inside one allocation |
| HyperQueue | a small server should fill Slurm workers |
| Snakemake | the work is a graph of files |
| Slurm array | every task is the same batch script with a different index |
| FireWorks | tasks must be stored and shared through a database |

#+begin_export latex
\begin{itemize}
\item QCG-PilotJob runs the tasks inside one allocation.
\item HyperQueue fills Slurm workers from a small server.
\item Snakemake rebuilds files that are missing or old.
\item Slurm array is one submission of the same script.
\item FireWorks records tasks in a database.
\end{itemize}
#+end_export

## Solution

A successful run ends with =qcg-finished= and =task-0=. The working directory is a temporary directory the script creates, so you will not see =out_0.txt= in the lesson tree afterwards. The three task names inside the script are =job_0=, =job_1=, and =job_2=.
